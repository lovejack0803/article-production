# 第6部 4-finish（仕上げ）

採用された指摘を原稿に反映し、完成原稿と Google ドキュメントにする。ドキュメントは、確認したフォルダにだけ作る。共有・コメント・メンション、記事管理表への書き込みは、人の確認が出るまでしない。

## 事前チェック

状態はステータス列では見ない。セルに値があるかで判断する。

1. 「指摘一覧」タブが無ければ止まる（チェックが終わっていない）。データ行が無い（見出しだけ）なら、反映する指摘は無いものとして先へ進む。
2. データ行は、J列（採否）がすべて「採用」か「不採用」であるときだけ進む。空の行、またはそれ以外の値があれば、行番号と値を示して止まる。
3. 採用かつ、指摘内容か該当箇所に【要一次情報】があり、修正案も K列（人のメモ・一次情報）も空の行があれば、その行番号を示して止まる（反映する文が無い）。
4. `'執筆'!B2:B6` のどれかが空なら止まる。`'完成原稿'!B2` に値があれば、上書きしてよいか聞く。B1は数式なので書かない。
5. 記事管理表のURLがこの会話に無ければ、書く直前に聞く（この時点ではまだ書かない）。

## 流れ

| 手順 | 担当 | 出力 |
|---|---|---|
| 1 | 自分 | 採用分を反映した `title_parts.txt`, `body.html`, `prose.txt`, `final.html` |
| 2 | 自分 | mech_check.py の結果をログ |
| 3 | 自分 | `'完成原稿'!B2` |

| 5 | 自分 | 見出しごとの内部リンクと CTA |

## 1. 採用した指摘を反映する

執筆の5セルを作業用の文字列にする（シートにはまだ書き戻さない）。採否が「採用」の行だけ、次の順で置き換える。

1. 修正案に文があれば、該当箇所を修正案にする。修正案が空で K列に文があれば、K列の文にする。どちらも空なら置き換えず、ログに「未反映」と残す。
2. 場所のセル（B2タイトル、B3導入文、B4本文、B5まとめ、B6メタ）の中で、該当箇所が1回だけなら、そこを置き換える。
3. 0回なら未反映としてログに残す。2回以上で、場所に見出しがあるときは、その見出しから次の同レベル以上の見出しの前まで、の最初の1回だけを置き換える。それでも1箇所に決まらなければ未反映とし、推測で選ばない。
4. 「不採用」の行は変えない。指摘一覧の J列・K列には書かない。

反映後の5セルから、原稿作成と同じ `body.html`（B4）、`title_parts.txt`（B2・B3・B5・B6）、`prose.txt`（導入文・本文・まとめ）を作る。続けて `final.html` を作る。本文に `<h2>まとめ` が無いときだけ、まとめの前に `<h2>まとめ</h2>` を置く。

```
<title>タイトル</title>
<p>導入文</p>
本文HTML
<h2>まとめ</h2>
<p>まとめ</p>
メタディスクリプション
<p>メタディスクリプション</p>
```

## 2. 機械チェックをやり直す

```
python3 -I mech_check.py --reg reg.json --project "<案件名>" --stage 本文 --file body.html --outline confirmed.json --kw "<メインKW>"
python3 -I mech_check.py --reg reg.json --project "<案件名>" --stage タイトル等 --file title_parts.txt --kw "<メインKW>"
python3 -I mech_check.py --reg reg.json --project "<案件名>" --stage 最終確認 --file prose.txt
```

`confirmed.json` が無ければ、本文のコマンドから `--outline` を外す。`reg.json` が無ければ、チェックと同じ読み方で作り直す。errors が残っても完成原稿には書く。件数と中身はログと報告に残す。

## 3. 完成原稿に書く

`write_range` で `'完成原稿'!B2` に `final.html` を書く。B1には書かない。読み直して一致するか確かめる。ログ：「仕上げ／反映」（採用件数、未反映の行番号）、「仕上げ／機械チェック」。

## 4. ドキュメントに変換する

変換規則は `html_to_blocks.py` が持つ。手でタグを読み替えない。作業フォルダへ、リポジトリの `article-production/html_to_blocks.py` を内容を変えずに置く。正本は https://github.com/lovejack0803/article-production/blob/main/article-production/html_to_blocks.py

```
python3 -I html_to_blocks.py final.html > blocks.json
```

スクリプトが出すブロックの意味は次のとおり（再実装しない。読むための対応表）。

| HTML | ブロック |
|---|---|
| `<title>` `<h1>` | `style: TITLE` |
| `<h2>` `<h3>` `<h4>` | `HEADING_2` `HEADING_3` `HEADING_4`。同じタグで整形後の文字列が同じ見出しは、先のものだけ残す |
| `<p>` と、タグにならない文 | `NORMAL_TEXT` |
| `<table>` | `table`。1行目は太字 |
| `<ul>` `<ol>` | `list`。`ordered` が false なら箇条書き、true なら番号付き。`level` は入れ子 |
| 見出しに 生成不要 / 未生成 / 事例のため / まとめのため / 手動執筆 | その見出しの直後に、太字・文字色 `#CC0000` の `NORMAL_TEXT`。「【執筆依頼】この見出しはAIで生成していません。構成案をもとに執筆をお願いいたします。」 |

文字の整形は、`<br>` を改行にし、残りのタグを除き、`&nbsp;` `&lt;` `&gt;` `&amp;` `&quot;` `&#39;` をこの順で戻す。`<p>` の直前にあるタグ無しの文に「メタディスクリプション」が含まれるとき、その `<p>` の先頭に「【メタディスクリプション】」を付ける。ラベルだけの文は段落にしない。`div` や `span` はタグだけ外し、中身は処理する。

保存先は、制作シートを置くフォルダと同じ決め方にする。

1. 今回の制作シートと、同じプロジェクトの他の行の作業シートを2〜3件 `get_file_metadata` で見る。共通の親フォルダを候補にし、その中の Google ドキュメント（過去の記事）を探す。見つかったドキュメントと同じフォルダを、新しいドキュメントの保存先の案にする。ファイル名は制作シートのタイトルに合わせる。
2. 案件名だけでフォルダを探すと、見つからないことがある。見つからないときも、候補があるときも、ドキュメントを作る前に必ず止まる。フォルダ名とリンクを示し、「このフォルダに保存してよいか、確認してください」と聞く。候補が無いときは、その旨を伝えてフォルダのリンクを求める。示すフォルダが無いのに「よい」とだけ返ってきても、作らない。
3. 「よい」と言われたら、そのフォルダに作る。別のフォルダのリンクが来たら、そのフォルダに作る。確認が来る前には `create_file` も `create_document` もしない。
4. 確認したフォルダにある既存のファイルは、移動しない。名前を変えない。中身を変えない。新しく作るドキュメントだけを、`create_file` でそのフォルダ（`parentId`）に空の Google ドキュメントとして作る（`contentMimeType` は `application/vnd.google-apps.document`）。タイトルは制作シートのタイトル。共有はしない。

中身の入れ方：

1. `blocks.json` の順に、`insert_text` で末尾へ足す（index は付けない）。段落は `paragraphStyle` にブロックの `style` を渡す。改行は新しい段落になる。
2. 執筆依頼の段落は `bold: true` で入れ、続けて `apply_text_style` の `textColor` を `#CC0000` にする。コメント機能は使わない。
3. リストは項目を1段落ずつ入れ（`level` の数だけ先頭にタブ）、その範囲を `create_list` にする。箇条書きは `BULLET_DISC_CIRCLE_SQUARE`、番号付きは `NUMBERED_DECIMAL_NESTED`。範囲は `firstItemText` と `lastItemText` で指定する。
4. 表は `insert_table` のあと、セルを読み直して右下から文字を入れる。1行目は `apply_text_style` で太字。行か列が20を超える表は、途中で切らず止まって人に伝える。
5. 内部リンクの URL は、段落を入れたあと `apply_text_style` の `linkUrl` でその文字列に付ける。メンション（@）は付けない。

## 5. 内部リンクと CTA

別スキルは呼ばない。構成案のリンク欄（その行の I列に値があれば I、空なら D）を、原稿作成までと同じ書式で読む。

```
内部リンク：
【案件名関連記事】記事タイトル
URL
→置き方
CTA：
【CTA】文言
URL
→置く位置
```

見出しの文字が一致する構成の行だけ置く。`→` に位置が書いてあればそこ（見出しの直下、など）。無ければ、その見出しの節の末尾（次の見出しの直前）に `NORMAL_TEXT` で置く。内部リンクは「【案件名関連記事】記事タイトル」のタイトル部分に `linkUrl`。CTA は「【CTA】文言」を1段落にし、URL があれば文言に `linkUrl`。`→` の行はドキュメントに出さない（作業用の指示なので）。URL が空の CTA は文言だけ置く。該当する見出しがドキュメントに無ければ、その件はログに残して飛ばす。

## 6. 記事管理表に原稿URLを書く

ここまでで一度止まる。ドキュメントの URL、記事管理表のタブ名、原稿URL列、行番号、いま入っている値を示し、次の文で確認する。

「この共有の記事管理表に原稿URLを書いてよいか。関係者にメール通知が行くことがあります。共有、コメント、メンションはしません。」

答えが出るまで `write_range` しない。書いてよいと言われたら、原稿URL列（見出し名が `原稿URL` の列。無ければ止まって見出しを示す）に URL の文字列を書く。スマートチップにできなくても、再試行で共有はしない。断られたときは URL をログに残して終わる。ドキュメントは、確認したフォルダに残す。

ログ：「仕上げ／ドキュメント」（ドキュメントURL、保存したフォルダの名前とリンク）、「仕上げ／原稿URL」（書いた、または確認待ちで止めた）。

## 完了と報告

報告は短く：

- 反映した指摘の件数と、未反映の行番号
- 機械チェックの errors、warnings、未検査（なければ「なし」）
- 完成原稿 B2 を書いたこと
- ドキュメントのタイトル、URL、保存したフォルダの名前とリンク
- 内部リンクと CTA の件数
- 記事管理表に書いたか、確認待ちで止めたか
