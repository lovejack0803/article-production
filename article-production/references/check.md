# 第5部 3-check（チェック）

執筆タブの原稿を直さず、直すべき点を指摘一覧に出す。人が採否を決める。article-check スキルは使わない。観点はこの部に書く。

## 事前チェック

状態はステータス列では見ない。セルに値があるかで判断する。

1. `'執筆'!B2:B6` を `read_range` で読む。1セルでも空なら止まる。どのセルが空かを伝える。B1とC列は数式なので、空かどうかの判断に使わない。
2. 事前調査の案件名とメインKWを読む。案件名が空なら止まる。
3. レギュレーションを読み直し、`reg.json` を作る。使う行は、有効が TRUE で、対象名が「共通」か事前調査の案件名（案件候補と揃えた表記）で、対象工程が本文・タイトル等・最終確認のもの。構成工程の行は使わない（構成は確定済み）。`--print-rules` の出力を `rules_body.txt`、`rules_title.txt`、`rules_final.txt` に保存する。
4. 執筆の5セルから、原稿作成と同じ形の `body.html`（B4）、`title_parts.txt`（B2・B3・B5・B6）、`prose.txt`（導入文・本文・まとめ）を作り直す。作業フォルダに古いファイルがあっても、シートの現在の値を使う。
5. この記事の制作シート以外は変えない。スプレッドシートIDが SKILL.md の設定値のテンプレートIDと同じなら、タブを足さず止まる。他のファイルへの複製や、共有フォルダの別シートへのタブ追加もしない。

## 流れ

3つのチェックは、担当ごとに読める範囲を分ける。Agent ツールがあれば、3人を同時に新しいエージェントへ渡す。無ければ、ファクト、レギュレーション、校正の順で自分で行い、前の担当のメモは開かない。重要度が「高」の指摘だけ、そのあと独立検証に出す。

| 手順 | 担当 | 読む範囲 | 出力 |
|---|---|---|---|
| 0 | 自分 | 執筆 B2:B6、事前調査、レギュレーション | `body.html`, `title_parts.txt`, `prose.txt`, `rules_*.txt` |
| 1a | ファクト担当 | 執筆 B2:B6、構成案の内容・出典（確定側。空ならAI案）、出典URL | `findings_fact.json` |
| 1b | レギュレーション担当 | 執筆のファイル、`rules_*.txt`、mech_check.py の結果 | `findings_reg.json` |
| 1c | 校正担当 | 執筆 B2:B6 だけ | `findings_proof.json` |
| 2 | 自分 | 3つの findings | 重要度を付けた `findings.json` |
| 3 | 独立検証担当 | 高の指摘1件につき、該当箇所とURLだけ | `verify_<No>.json` |
| 4 | 自分 | `findings.json` と検証結果 | 指摘一覧タブ、ログ |

執筆タブには書かない。修正は指摘の「修正案」だけに置く。

指摘1件の形（3担当共通。JSON配列。指摘が無ければ `[]`）：

```
[{"place":"B4 / 費用の目安","quote":"原稿からの引用","note":"何が問題か","fix":"修正案。数値が未確認なら空","url":"https://...","severity":"高"}]
```

- place：セル（B2タイトル、B3導入文、B4本文、B5まとめ、B6メタ）と、本文なら見出し。
- severity：高＝数値や主張が一次資料と食い違う、出典の無い数値・事例、【要一次情報】、機械チェックの errors、意味が変わる誤字、レギュレーションの禁止。中＝（目安）の警告、表記ゆれ。低＝意味が変わらない読みやすさの提案。
- 根拠のURLを開けていない指摘は、url を空にし、note に「未確認」と書く。数値を推測で埋めない。

## 1a. ファクト担当

```
あなたは事実確認の担当です。記事の主張と数値を、出典で確かめます。
読んでよい範囲：スプレッドシート {{シートID}} の '執筆'!B2:B6 と、構成案の内容・出典（行ごとに G〜K に値があればそこ、空なら B〜F の E列に相当する内容・出典）。引用されているURLは Web 検索とページ取得で開いてよい。
出力：findings_fact.json。最終回答は「完了」と、高の件数だけ。

# 手順
1. 原稿から、数値・固有の事例・「公式には」「データでは」などの主張を抜き出す。
2. 構成に書いてある出典URLを先に開く。無ければ Web 検索し、官公庁・事業者公式・論文など一次資料を優先する。二次記事だけで数値を確定しない。
3. 一次資料と食い違う箇所、出典を開いても裏が取れない箇所を指摘にする。原稿に【要一次情報】とある箇所は、裏が取れても取れなくても1件ずつ残す（人が内容を書く行にするため）。
4. 修正案に、開いて確認した数値だけを書く。確認できなければ修正案は空にし、指摘内容を【要一次情報】とする。
```

## 1b. レギュレーション担当

親は `reg.json` と、シートから作り直した3ファイルを用意する。機械チェックの実行と、シートに無いルールの判定は、この担当が行う。`confirmed.json` が無いときは `--outline` を付けない。

```
あなたはレギュレーションの適合を見る編集者です。案件名は「{{案件名}}」、メインKWは「{{メインKW}}」です。
読んでよい範囲：作業フォルダの body.html, title_parts.txt, prose.txt, rules_body.txt, rules_title.txt, rules_final.txt, reg.json, mech_check.py。confirmed.json があるときだけ、それも読んでよい。
出力：check_body.json, check_title.json, check_final.json（機械チェックのJSONそのまま）と findings_reg.json。

# 手順
1. 次を実行し、標準出力をそのまま保存する。confirmed.json が無いときは本文のコマンドから --outline を外す。
   python3 -I mech_check.py --reg reg.json --project "{{案件名}}" --stage 本文 --file body.html --outline confirmed.json --kw "{{メインKW}}"
   python3 -I mech_check.py --reg reg.json --project "{{案件名}}" --stage タイトル等 --file title_parts.txt --kw "{{メインKW}}"
   python3 -I mech_check.py --reg reg.json --project "{{案件名}}" --stage 最終確認 --file prose.txt
2. errors は1件につき指摘1件。severity は高。（目安）の warnings は中。JSON の unsupported は指摘にしない（親がログの未検査に書く）。
3. rules_*.txt のうち、スクリプトが判定しない文（です・ます、体言止め、表記、禁止語など）を原稿に当てはめる。違反だけを指摘にする。
4. 修正案は、ルールに合う短い直し。原稿全体の書き換え案は書かない。事実の裏取りはしない（ファクト担当の範囲）。
```

## 1c. 校正担当

```
あなたは校正者です。誤字脱字、文法、表記のゆれを見ます。
読んでよい範囲：スプレッドシート {{シートID}} の '執筆'!B2:B6 だけ。Web もレギュレーションも開かない。
出力：findings_proof.json。

# 手順
1. 誤字、助詞の誤り、文のねじれ、送り仮名、漢字とかなのゆれ、数字や括弧のゆれを拾う。
2. 意味が変わる誤字は severity を高、ゆれは中、好みの言い換えは低にする。低は、直さないと読めないものだけに限る。
3. 事実が正しいか、レギュレーションの文字数は見ない。
```

受け取ったら、3ファイルが JSON 配列として読めるか確かめる。欠けていれば同じ担当に1回だけ直させ、だめならその担当分を空配列にしてログに「停止」と残し、他の担当の結果で先へ進む。

## 2. 指摘をまとめる（自分）

3ファイルを `findings.json` に連結する。種別はファクト、レギュレーション、校正。No は 1 からの連番。同じ引用で種別が違うものは、両方残す。重要度が「高」のものだけを独立検証に回す。高が無ければ検証はしない。

## 3. 独立検証担当

高の指摘は1件ずつ、新しいエージェントに渡す。渡してよいのは、場所、該当箇所、指摘を1文にしたもの、根拠URLだけ。なぜそう判断したかのメモ、修正案の理由、他の指摘は渡さない。

```
あなたはこの箇所を初めて確認する検証者です。前の担当の判断過程は渡されていません。
読んでよい範囲：下の該当箇所と、根拠URL（あれば開く）。それ以外のファイルは開かない。
出力：verify_{{No}}.json（{"result":"維持"|"取り下げ"|"修正","note":"1〜2文","url":"開いたURL","fix":"修正するときだけ"}）。

# 材料
場所：{{place}}
該当箇所：{{quote}}
確認してほしい点：{{note を1文}}
URL：{{url}}

# 手順
1. URLがあれば開く。無ければ、その主張の一次資料を Web 検索で1件だけ探す。見つからなければ result は維持、url は空。
2. 該当箇所の問題が残るなら維持。問題が無ければ取り下げ。引用の読み違いだけなら修正とし、fix に短い案を書く。
3. 数値を推測で作らない。
```

`result` をその指摘の独立検証結果に書く。修正のときは、指摘内容と修正案とURLを、検証結果で置き換える。高以外の独立検証結果は「未実施」。

## 4. 指摘一覧へ書く（自分）

1. `get_spreadsheet` で、いまの制作シートに「指摘一覧」タブがあるか見る。
2. 無ければ `add_sheet_tab` でこのスプレッドシートにだけタブを足す。続けて A1:K1 に見出しを1行書く。列名は、No、種別、場所、該当箇所、指摘内容、修正案、根拠・出典URL、重要度、独立検証結果、採否、人のメモ・一次情報。
3. タブが既にあるときは A1:K1 を読む。上の列名と違えば、実際の見出しを示して止まる（列を推測でずらさない）。
4. A2:I に値がある行があれば、行数と先頭数件を示して、上書きしてよいか聞く。答えが出るまで消さない。J列とK列は、値があっても消さないし書かない。
5. 上書きが承認された、またはデータ行が無いときだけ、バックアップを取ってから、`clear_range` で A2:I を消し、`write_range` で A2 から、各行 `[No, 種別, 場所, 該当箇所, 指摘内容, 修正案, 根拠・出典URL, 重要度, 独立検証結果]` を書く。JとKは空のまま。
6. 読み直して `findings.json` と一致するか確かめる。
7. ログ：「チェック／ファクト」「チェック／レギュレーション」（errors／warnings／unsupported の件数）、「チェック／校正」「チェック／独立検証」（高の件数と、維持・取り下げ・修正の内訳）、「チェック／確定」（書いた行数、タブを新設したか）。

## 完了と報告（人の確認②）

指摘を書いたら止まる。執筆タブは変更していないことを伝える。報告は短く：

- 指摘の件数（種別ごと）と、重要度が高で独立検証が維持・取り下げ・修正の件数
- 【要一次情報】の行番号
- 機械チェックの未検査の指定（なければ「なし」）
- 指摘一覧タブのリンク
- 次にやること：「J列（採否）を記入してください。【要一次情報】の行は、K列（人のメモ・一次情報）に内容を書いてください。済んだら『仕上げて』と指示してください」

指摘が0件のときは、見出しだけのタブを用意し、「指摘はありません。採否の記入は不要です。『仕上げて』と指示してください」と伝えて止まる。
